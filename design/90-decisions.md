### 2026-08-30 — `/information` is served `no-store`; an absent header buys sixty seconds of caching, not none
Context: this supersedes the 2026-08-30 entry *The endpoint advertises no positive `max-age` on `/information`* below, whose premise is false. That entry chose to advertise nothing, on the stated ground that `winget-cli`'s parsed default for an absent `Cache-Control` header is immediate expiry. It is not. Verified in the `winget-cli` working tree at `5c88b96f`: an absent header returns early from the policy constructor leaving every field unset (`src/AppInstallerCommonCore/Downloader.cpp:643-648`); the policy reaches the information cache regardless (`src/AppInstallerRepositoryCore/Rest/RestClient.cpp:153,161,171`); the cache declines to store only on `no-store` or `no-cache` (`src/AppInstallerRepositoryCore/Rest/RestInformationCache.cpp:81-84`); and a zero `max-age` is read as *no expiration information provided* and replaced with sixty seconds (`RestInformationCache.cpp:30-38`). Silence therefore buys the weaker guarantee while appearing to buy the stronger one, and how long a client may believe a revoked or reconfigured source is a security-relevant lever.
Chosen: serve `/information` with `no-store`, which the client honours explicitly. Named fallback: if the pinned runtime release and the HTTPS termination arrangement between them cannot set that header, the sixty-second default is accepted, stated in the operations documentation as the bound on client staleness, and recorded — not discovered later.
Rejected: Advertising nothing and relying on the client default — rejected on the evidence above; it is the superseded choice. A positive `max-age` — rejected because a reconfiguration or revocation would then take effect at a chosen later time, differently per client. `no-store` as a hard deployment requirement with no fallback — rejected because it lets an unverified property of the termination arrangement veto the runtime this brief pins, whereas the fallback bounds the exposure at sixty seconds and makes that bound visible.
Reversibility: cheap — one response header on one endpoint, and the client re-reads it on the next request by construction.

### 2026-08-30 — Restorability is the whole recovery requirement; there is no objective in time
Context: `design/self-hosted-source/00-brief.md` requires recovery to be proven rather than designed, and the 2026-08-29 decision settling the backup destination and the split by provenance left the third part of that handoff item — the recovery objective — unstated. A periodic re-proof on a schedule — rejected because a cadence invented where no objective exists is a requirement nobody agreed to, which is skipped once and then quietly dropped; an existing proof is instead retired by the environment moving, under the licensing rule `design/10-design.md` § *Environment* already establishes. Leaving the question open — rejected because it blocks every slice touching backup or restore procedure, for an answer only the maintainer holds.
Reversibility: cheap. Adding an objective later tightens a procedure and adds a rehearsal cadence; it invalidates no stored data and no published identifier.

### 2026-08-30 — Mirrored packages keep the upstream identifier, and the source is registered `Explicit`
Context: `design/self-hosted-source/00-brief.md` admits both first-party and mirrored packages into one source, and requires that source be registered explicitly so it cannot silently compete with `winget` or `msstore`. Those two requirements pull against each other: a mirror carrying the upstream `PackageIdentifier` is an identifier that now exists in two configured sources.
Chosen: mirrors keep the upstream `PackageIdentifier` verbatim, and the source is registered with WinGet's `Explicit` property. `Explicit` is a first-class client property, not a usage convention — in `winget-cli` at `5c88b96f`, an explicit source is filtered out of any operation that does not name it (`src/AppInstallerRepositoryCore/Public/winget/RepositorySource.h:157`, `src/AppInstallerRepositoryCore/RepositorySource.cpp:547,563`), and the built-in font source already ships this way (`src/AppInstallerRepositoryCore/SourceList.cpp:412`). Non-competition is therefore enforced by the client rather than by choosing a different identifier, and the accepted consequence is that an unqualified `winget upgrade` never consults this source: the mirror is a deliberate fallback, not an automatic one.
Rejected: A namespaced mirror identifier — rejected because `winget upgrade` matches an installed package by its identifier, so a namespaced mirror cannot serve a machine that already has the package, which is precisely the situation the brief's problem statement describes; it would be a new package that happens to contain the same software. A suffix on the mirrored version — rejected for the same reason, and because it corrupts version ordering as well. Registering the source non-explicitly and relying on always passing `--source` — rejected because a discipline that must be remembered on every command is not the non-competition guarantee the brief asks for.
Reversibility: cheap for the registration flag, expensive for the identifier. Changing `Explicit` is one `winget source update` per client; changing a published identifier orphans every machine that installed under the old one.

### 2026-08-30 — Provenance is derived from the manifest tree's shape, not declared in a field or an index
Context: the 2026-08-29 backup split makes provenance load-bearing — first-party bytes are backed up because they cannot be re-obtained, mirrored bytes deliberately are not. Something therefore has to say which class a package belongs to, and the WinGet manifest schema is external and fixed.
Chosen: provenance is derived from the manifest's position in the manifest tree, one subtree per class, with membership being the whole of the fact. Nothing else records it.
Rejected: A custom manifest field — rejected because `winget validate` rejects unknown fields, so it would fail the gate that makes a manifest trustworthy at all. A sidecar index — rejected because it is a second copy of something the tree already states, and the copy is the half that rots. Inferring from the publisher name — rejected because a mirror of the maintainer's own software published elsewhere would be misclassified, turning provenance into a guess. Named fallback: if the pinned runtime release turns out to require a layout that cannot express two subtrees, provenance moves to a sidecar index and the second rejection is accepted as a cost — the design does not assume a layout it has not verified.
Reversibility: cheap. Provenance is currently unreferenced by anything outside the backup procedure, so moving it is a move of files plus one procedure edit.

### 2026-08-30 — The host is a rebuildable projection; only the private key and the Entra registration are irreplaceable
Context: the brief requires recovery to be proven rather than designed — a first-party installer restored from backup, a manifest revision rolled back, and a clean client installing after the restore. That is only achievable if what has to be recovered is bounded and named.
Chosen: the host holds no source of truth. Its served state is a projection of a named repository commit plus the artifact store, and the runtime's own working state is treated as disposable. The only host state that cannot be reconstructed from Git and the artifact store is the certificate private key and the Entra registration in the tenant, and both are named so their absence is visible. Because "which commit is served" is an answerable question, host evidence can be time-bounded the same way runner-image evidence is in `design/10-design.md` § *Environment*.
Rejected: Serving directly from a working clone on the host — rejected because it makes the served state a mutable thing with no name, so the commit that produced an observation stops being recoverable and every piece of host evidence loses its boundary. Treating the host as authoritative and syncing back — rejected because it puts installer bytes and unreviewed manifests upstream of Git, which the brief forbids outright.
Reversibility: cheap while the deployment is one host; the projection is a deployment-configuration choice, not a data migration.

### 2026-08-30 — Publication is ordered artifact-then-manifest, advances atomically, and ends at an observed refresh
Context: the manifest store and the artifact store cannot hold each other's content, so a package is only whole when both agree. Two half-states are possible and they are not equally bad, and clients read the source concurrently with every change to it.
Chosen: publish in the order bytes → backup, if first-party → manifest merged → served set advanced → refresh observed; withdraw in the exact inverse, bytes last. The served manifest set advances from one commit to another as a single step. The final step of a publication is an observation of what the source now serves, not an assumption that the runtime noticed. Specifying the observation rather than the mechanism is deliberate: whether the pinned release watches its directory or must be restarted is a property of that release, which this repository does not own and has not verified.
Rejected: Manifest-first — rejected because it publishes a broken package on a live source, where the accepted direction leaves only an unreferenced artifact, which is inert. Synchronising files in place — rejected because a client reading mid-synchronisation sees a manifest set that never existed as a commit, and the resulting failures are intermittent and unreproducible, the worst possible class of failure for a system whose entire output is recorded evidence. Ending a publication at the projection advance — rejected because it records a refresh that was never observed, which is the fabricated gate result `AGENTS.md` § *Verification* exists to prevent.
Reversibility: cheap. It is an ordering in a procedure and a property of one deployment-configuration choice.

### 2026-08-30 — The endpoint advertises no positive `max-age` on `/information`
**Superseded** by *`/information` is served `no-store`; an absent header buys sixty seconds of caching, not none* (2026-08-30, above). The `Chosen` paragraph below states an external fact that the code contradicts; it is retained unedited because this log is append-only, and it must not be cited.

Context: a client's belief about this source's authentication type, advertised Entra resource, and supported versions comes from `/information`, not from the repository. How long a client may hold a stale copy of that is therefore a security-relevant lever, and it is set by the server.
Chosen: advertise no positive `max-age` on `/information`, keeping the client's default. In `winget-cli` at `5c88b96f` the response is cached only as `Cache-Control` directs, and the parsed default when the header is absent is immediate expiry (`src/AppInstallerRepositoryCore/Rest/RestInformationCache.cpp`, `src/AppInstallerCommonCore/Public/AppInstallerDownloader.h:122-137`). Rejected: A long `max-age` — rejected because an authentication or version change would take effect at an unknown later time, differently per client, and a client could keep a working view of a source that has been reconfigured or revoked. Depending on `no-store` specifically — rejected because relying on a header the pinned release may not emit is a weaker guarantee than relying on the absence of one, even though the client honours both.
Reversibility: cheap — it is one response header on one endpoint, and the client re-reads it on the next request by construction.

### 2026-08-29 — The self-hosted source is a repository-asset boundary, not a library capability
Context: `design/proposals/self-hosted-repository/handoff-to-opus.md` names its first required outcome as a choice between two shapes — deployment assets in this repository with `rewinged` external, or a first-party hosted-service capability requiring a product and contract amendment. Left undecided, no brief could be written, because the two shapes have different owners, different non-goals, and different stop conditions.
Chosen: the repository-asset boundary. This repository gains declarative package manifests, deployment configuration, operations documentation, and validation scripts. `rewinged` stays an external, independently deployed runtime that this repository does not own, vendor, fork, or wrap. No public `SubZeroDev.WinGet` API is added and the service/client/COM dependency direction is unchanged, so the handoff's first stop condition does not fire. The work is authored in parallel with the in-flight v0.2 sequence rather than after it.
Rejected: A first-party hosted capability — rejected because it makes the library responsible for serving packages, which is precisely the handoff's stop condition, and commits public surface that is expensive to reverse.
